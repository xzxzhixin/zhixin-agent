# 记忆召回与富文本输入框关联设计

## 背景

用户确认“记忆召回缺失”和“对话框输入框富文本化”有关联，但关联点不是输入框直接参与记忆召回。正确边界是：输入框负责产生结构化消息草稿；消息发送后，中心服务把文本、附件和代码引用固化为正式消息事实；轮次完成后，记忆系统从正式消息事实中写入长期记忆；后续任意窗口对话前，再由 Mem0、SQLite 记忆索引和 Markdown 记忆共同召回。

## 已确认口径

- 输入框内部不直接读写长期记忆。
- 发送前的临时附件、引用和文本只属于草稿，不能进入永久记忆。
- 发送后，文本、附件、代码引用和 IDE 选区引用都成为正式消息事实。
- 记忆写入采用两层：先保存附件来源引用，再对可解析附件异步追加内容摘要。
- 附件文件只保存一份，进入记忆归档附件目录；会话消息和长期记忆都引用同一份归档附件。
- 删除会话时只删除会话与归档附件的引用关系，不删除归档附件文件。

## 目标

- 修复跨窗口记忆召回缺失，例如窗口 A 中用户说“我今天吃了龙虾”，窗口 B 中用户问“我今天吃了什么”时，大模型能够通过长期记忆召回答复“龙虾”。
- 富文本输入框支持在光标位置插入附件、代码引用、文件引用和 IDE 选区引用，但不把草稿阶段内容写入长期记忆。
- 附件作为长期记忆来源保存，能解析的附件保存内容摘要，不能解析的附件也保留来源引用。
- 记忆召回不能靠固定问题、固定关键词或具体业务文本硬编码完成。

## 非目标

- 不在本设计中实现附件解析模型或 OCR 的具体供应商选择。
- 不在本设计中定义附件归档清理 UI。
- 不把临时草稿附件提前写入记忆。
- 不把输入框组件直接耦合到 Mem0、SQLite 或 Markdown 记忆写入逻辑。

## 总体方案

采用“结构化消息事实 + 单份归档附件 + 异步附件摘要”的方案。

输入框草稿在前端保持结构化：

- 文本片段。
- 附件片段。
- 项目文件、文件夹、代码位置和 IDE 选区引用片段。
- 光标位置和片段顺序。

发送时，中心服务把临时附件转为归档附件，并把草稿片段固化为正式用户消息。正式消息既保留用于前端展示的 Markdown，也保留用于记忆、附件、引用和审计的结构化来源关系。

轮次完成后，记忆写入只消费正式消息事实。文本事实立即写入长期记忆；附件引用立即写入长期记忆；附件内容摘要由异步解析任务补充写入。

## 附件存储设计

临时附件保存位置：

```text
center-data/temp
```

正式归档附件保存位置：

```text
center-data/memory/attachments/{year}/{month}/{day}/{attachmentId}/{originalFileName}
```

路径时间使用中心服务本机时间，格式来源与现有记忆写入一致。

附件从草稿转正式消息时，中心服务执行：

1. 校验临时附件仍在 `center-data/temp`。
2. 生成正式 `attachmentId`。
3. 把文件移动到 `center-data/memory/attachments` 归档目录。
4. 写入正式附件元数据。
5. 写入会话消息与归档附件的引用关系。
6. 写入后续记忆写入可追溯的来源关系。

会话消息引用归档附件，不再保存独立会话附件副本。记忆也引用同一个归档附件。

## 会话引用设计

会话侧需要保存以下引用关系：

- `sessionId`：来源会话。
- `turnId`：来源轮次。
- `messageId`：来源用户消息。
- `attachmentId`：归档附件 ID。
- `attachmentName`：用户可见附件名。
- `archivePath`：归档附件相对中心目录路径。
- `mimeType`：附件 MIME 类型。
- `sizeBytes`：附件大小。

删除会话时，只删除会话、消息、轮次、任务和会话附件引用关系，不删除 `center-data/memory/attachments` 下的归档文件。

## 记忆写入设计

轮次完成后，记忆写入分为两层。

第一层立即写入：

- 用户文本中的稳定事实。
- 附件来源引用，例如附件名、附件 ID、来源会话、来源轮次、来源消息。
- 项目文件、代码位置和 IDE 选区引用来源。

第二层异步写入：

- 图片摘要。
- PDF 或文档摘要。
- 音频转写摘要。
- 视频或其他媒体的可用元数据摘要。

附件摘要成功后，追加到同一个附件来源链路。附件摘要失败时，写入审计事件，不影响主轮次终态，也不能删除已经写入的附件来源引用。

## 记忆召回设计

每次大模型对话前，中心服务构造记忆召回查询：

- 使用当前用户问题作为主要查询文本。
- 同时检索 Mem0。
- 同时检索 SQLite `memory_index`。
- 通过 SQLite 结果回查 Markdown 记忆来源。
- 合并、去重、过滤低质量结果后注入模型系统上下文。

召回内容至少包含：

- 事实正文或附件摘要。
- 来源会话 ID。
- 来源轮次 ID。
- 来源消息 ID。
- 关联附件 ID 和附件名。
- Markdown 记忆路径。

身份类、偏好类、当天事实类和附件内容类问题都走同一套召回策略，不允许通过“我是谁”“你叫什么”“龙虾”等固定问题或业务词硬编码召回。

## 富文本输入框设计边界

富文本输入框负责编辑体验：

- 文本和附件可按光标位置混排。
- 文件、文件夹、代码位置和 IDE 选区引用可按光标位置插入。
- 附件在发送前显示图标、文件名、缩略图或类型标识。
- 输入框保持片段顺序，发送时交给中心服务。

输入框不负责：

- 长期记忆写入。
- Mem0 调用。
- SQLite 记忆索引写入。
- Markdown 记忆文件追加。
- 附件内容摘要生成。

## 数据边界

中心服务仍是唯一事实源。客户端不能直接写归档附件、长期记忆、SQLite 索引或 Mem0。

Worker 和 Deep Agents 不能直接写核心 SQLite 或归档附件目录。它们只能通过中心服务能力请求附件读取、附件摘要、记忆写入或召回。

## 删除与清理边界

删除会话：

- 删除会话消息。
- 删除会话附件引用。
- 不删除归档附件文件。
- 不删除已经写入的长期记忆。

删除记忆或清理附件：

- 本设计只定义后续需要独立生命周期。
- 没有任何会话、记忆或索引引用的归档附件可以成为清理候选。
- 删除归档附件属于危险操作，执行前必须确认。

## 验收口径

### 跨窗口文本记忆

1. 窗口 A 发送：`我今天吃了龙虾`。
2. 等待轮次完成并写入长期记忆。
3. 窗口 B 发送：`我今天吃了什么？`。
4. 模型通过长期记忆回答用户今天吃了龙虾。

### 附件来源记忆

1. 窗口 A 上传附件并发送。
2. 临时附件从 `center-data/temp` 转移到 `center-data/memory/attachments`。
3. 会话消息保存对归档附件的引用。
4. 长期记忆保存附件名、附件 ID、来源会话、来源轮次和来源消息。

### 附件摘要记忆

1. 对可解析附件生成内容摘要。
2. 摘要追加到同一附件来源链路。
3. 窗口 B 能根据附件内容摘要召回回答。
4. 摘要失败时，附件来源引用仍可召回，主轮次不被改成失败。

### 删除会话

1. 删除包含附件的会话。
2. 会话引用被删除。
3. 归档附件文件仍存在。
4. 已写入的长期记忆仍能追溯附件 ID 和归档路径。

### 草稿边界

1. 用户粘贴附件但不发送。
2. 附件只存在于临时草稿。
3. 长期记忆、SQLite 记忆索引和 Mem0 都不能出现该附件。

- `功能清单与关系.md`：新增或修订“富文本输入框结构化消息事实”“归档附件引用”“附件记忆写入”“跨窗口记忆召回”相关功能关系。

`总体计划.md` 标注仅用户可修改，本设计不修改该文件。

- 附件只保存一份的目录口径已明确。
- 会话删除和归档附件删除边界已明确。
