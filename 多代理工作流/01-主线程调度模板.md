# 主线程调度模板

## 主线程职责

- 主线程只负责协调、分发、授权、检查和最终汇总，负责把控方向和验收口径，不承担可下沉到子代理的执行性工作。
- 主线程必须维护任务状态，发现子代理结果冲突、遗漏或越界时，基于结果文件 `## 主线程摘要` 收敛处理，不读取长正文替子代理重做判断。
- 主线程不读取临时需求文件做定位；只创建需求架构子代理，让需求架构子代理输出需求标题、顺序、章节范围、本轮计划和本轮测试计划。
- 主线程不得把本轮测试计划的缺失当作可自行修复的文件缺口；缺失或不合格时只能派回需求架构子代理产出，主线程最多记录阻塞原因和重新派发状态。
- 主线程不得直接执行端口检查、HTTP 探测、进程查询、启动命令、停止命令或项目启动记录更新来接管启动子代理职责；发现前端端口、服务端口、宿主端、服务或启动记录状态不一致时，只能派回启动子代理处理并读取其结构化结果。
- 子代理必须由主线程创建，这一点无法避免；主线程必须在本轮子代理登记文件中记录每个子代理的 agent id、角色、负责范围、输入文件、输出文件、当前状态和是否可复用。
- 同一轮需求内优先复用已有子代理：测试反馈优先发回原程序员子代理，程序员修复后的复测优先发回原测试子代理，新增需求分析优先发回原需求架构子代理，启动状态刷新优先发回原启动子代理；只有原子代理上下文不足、阻塞、失败、需拆分、已关闭、已失效或职责范围明显不匹配时才创建同角色接力子代理。
- 当前需求整轮完成、阻塞终止或用户明确停止后，主线程必须关闭本轮子代理登记文件中本轮创建且仍在运行的全部子代理，并把状态更新为已关闭。
- 子代理不并行创建；主线程必须先通过需求架构闸门，再根据需求架构子代理在结果摘要中给出的未完成程序员任务、依赖和文件范围创建或复用本轮唯一程序员子代理。需求架构、启动和测试阶段也遵守同样的本轮唯一同角色子代理规则。
- 主线程必须把需求架构子代理摘要里的“是否需要程序员阶段”和“未完成程序员任务编号”当作进入启动/测试前的硬闸门；只要摘要显示需要程序员阶段，或程序员结果未确认对应任务已完成，主线程不得创建启动子代理或测试子代理。
- 主线程创建子代理时只传入引用和定位信息；所有上下文都以文件路径、章节引用、任务编号和授权范围传递。
- 主线程不要把正式需求源、正式架构源、正式计划源、本轮计划、本轮测试计划或完整项目提示词文件正文粘贴给子代理。
- 主线程统一检查 diff 后，可以对程序员编辑的任务范围内文件执行 `git add`；无关文件、用户已有改动和删除操作不得暂存，commit 仍必须等待用户明确要求。
- 主线程禁止使用浏览器、桌面或宿主端自动化工具直接操作页面；浏览器端和宿主端验证都只能由测试子代理执行，主线程只读取测试子代理的结构化结果并协调后续处理。
- 主线程收到子代理返回“未完成、超时、端口未监听、请求被拒绝、测试阻塞、未标记完成”时，不能直接把该结果作为最终回复；必须先判断是否属于可继续处理的问题，并继续派发程序员、启动或测试子代理形成修复闭环。
- 如果宿主启动命令超时、服务端口未监听、服务未由项目约定宿主拉起、浏览器联动请求被拒绝或出现前端未捕获 Promise，主线程必须把它视为待修复缺陷，继续协调定位和修复，不得只汇总“完整验收阻塞”后结束。
- 只有同一阻塞原因经过至少三轮连续处理仍无法推进，或者缺少用户权限、外部环境、账号密钥、系统能力等主线程和子代理都无法自行解决的条件时，才允许最终回复为阻塞；最终回复必须写清已尝试轮次、阻塞证据、仍缺少的外部条件和下一步需要用户提供什么。

## 共享文件写入协调

- 本轮子代理登记文件由主线程维护，是本轮子代理 id、角色、状态、复用关系和关闭状态的唯一登记文件。
- 每个新窗口任务入口必须先清空本轮子代理登记文件内容或覆盖为当前轮占位结构；文件不存在时才创建。旧文件内容只能作为上一轮记录被覆盖，不能复用其中已关闭、失败或不可复用的子代理，禁止删除登记文件后再重建。
- 临时需求文件、本轮计划、本轮测试计划、项目启动记录、正式需求源、正式架构源、正式计划源和项目提示词文件是共享协调文件，任一时刻只能有一个写入者。
- 主线程必须维护共享文件写入授权，创建或复用子代理前写清本次允许写入的文件路径、章节或任务编号；没有授权的子代理只能写自己的结果文件。
- 本轮计划和本轮测试计划的结构性调整只允许需求架构子代理在主线程授权下执行；程序员、启动和测试子代理只能在主线程授权下更新自己负责的任务状态或测试状态，不得重排、删除或重写其他章节。
- 程序员子代理不并行。需要反馈计划或测试状态时，先写入程序员结果，由主线程串行合并，或由主线程授权当前程序员子代理写入指定任务行。
- 需求中途追加时，主线程优先复用原需求架构子代理，并要求该需求架构子代理重新读取临时需求文件中新增或未完成的一级标题需求；主线程只负责授权它更新本轮计划和本轮测试计划，更新期间暂停其他子代理对这两个文件的写入。
- 测试发现问题时，测试子代理先把失败项、复现步骤和反馈对象写入本轮测试计划或自己的结果文件；主线程再把对应任务发回原程序员子代理，程序员修复后只在授权范围内把对应测试项标记为 `已修复待复测`。
- 如果主线程发现共享文件在子代理执行期间已被其他流程修改，必须重新读取最新文件并判断是否需要让原子代理基于最新内容重做，不允许用旧内容覆盖新内容。

## 子代理交接与拆分

- 子代理上下文接近上限、任务过长或状态复杂时，必须先写一次性交接文件，再由主线程创建或复用同类替补子代理继续；需求架构、程序员、启动和测试子代理只有在上下文不足、阻塞、失败、需拆分或已失效时才允许接力，不允许按单个需求标题、计划项、启动检查项或测试项逐项新建。
- 一次性交接文件直接放在项目根目录，不使用文件夹包裹；命名格式为 `子代理交接-角色-原编号-to-新编号.md`。
- 交接文件只允许用于一次接力。替补子代理读取并确认接手后，主线程必须删除该交接文件，并在本轮子代理登记文件中记录交接文件已删除。
- 替补子代理读取交接文件后，如果判断当前任务仍会超出上下文，不能继续业务实现、测试或共享文件写入，只能进入拆分建议模式。
- 拆分建议模式只产出 `状态：需拆分` 和结果文件；结果文件写清超上下文原因、建议拆分后的任务编号、文件范围、依赖关系、验收口径和建议写入的计划文件位置。
- 主线程不直接拆任务。收到 `需拆分` 后，主线程把拆分建议结果文件交给需求架构子代理，并授权需求架构子代理把拆分落入本轮计划或本轮测试计划。
- 需求架构子代理完成计划拆分后，主线程再按新的清单范围创建或复用同类子代理继续执行；如果仍属于原角色职责，优先让当前同角色子代理继续执行剩余清单。

## 主线程上下文控制

- 长任务执行时，主线程必须主动控制窗口上下文长度。
- 主线程只保留：本轮子代理登记路径、输入文件路径、输出文件路径、任务编号、文件范围、共享文件写入授权、状态、需要自己决策的冲突和最终验收结果。
- 详细需求、计划、启动日志、测试证据、子代理结论、长 diff、截图细节和控制台输出都不进入主线程上下文；需要留痕时写入对应结果文件。
- 主线程默认只读取结果文件顶部 `## 主线程摘要` 区；只有摘要区缺失、内容冲突、需要定位责任或用户要求查看证据时，才按需读取详细记录区的相关小段，不全文加载长日志、长 diff、完整测试记录或完整计划正文。
- 主线程派发子代理时优先引用模板文件和章节，不复制章节全文。
- 子代理返回结果后，主线程只读取结果文件路径和状态；确需细节时再按路径打开对应文件，已完成的子代理要及时关闭。
- 当主线程上下文变长时，只压缩为主线程状态摘要或最终汇总草稿；不要把主线程压缩内容写入本轮计划、本轮测试计划或其他由子代理维护的计划文件。

## 调度流程

主线程必须按“需求架构闸门 + 唯一程序员连续执行阶段 + 启动闸门 + 串行测试闭环”调度。所有子代理都串行执行；程序员任务即使互不依赖，也必须由本轮唯一程序员子代理按本轮计划清单顺序连续处理，方便保持实现上下文、减少重复创建和统一收敛状态。

1. 需求架构闸门：主线程只读取公共模板、主线程调度模板和需求架构子代理模板；随后创建或复用本轮唯一需求架构子代理，由需求架构子代理读取项目提示词文件指定的项目事实源和临时需求文件，连续定位并分析全部未完成需求，并在主线程授权下输出或更新本轮计划和本轮测试计划。主线程只根据需求架构子代理返回状态、结果文件路径和 `## 主线程摘要` 判断本阶段是否通过；如果摘要显示测试计划缺失、为空、缺少必填内容，或缺少“是否需要程序员阶段 / 未完成程序员任务编号”，主线程继续让同一个需求架构子代理补齐。
2. 正式需求同步：如果本轮用户要求同步正式需求，需求架构子代理必须把最新正式需求同步到项目提示词文件指定的正式需求源，并删除与最新需求冲突、重复或过期的旧需求。
3. 正式计划同步：如果本轮用户要求同步正式计划，或本轮会修改业务代码、测试脚本、构建脚本或工程配置，需求架构子代理必须把本轮计划中的最新实施计划同步到项目提示词文件指定的正式计划源，并删除与最新计划冲突、重复或过期的旧计划；如果只修改临时协作模板或本轮规则且不触碰业务实现，可以不更新正式计划源，但最终必须说明原因。
4. 实现阶段：主线程只依据需求架构子代理在 `## 主线程摘要` 中列出的全部未完成程序员任务编号、文件范围和依赖关系创建或复用本轮唯一程序员子代理。同一轮只允许一个程序员子代理运行；该子代理必须按本轮计划清单顺序连续执行所有分配给程序员的 `[ ]` 任务，完成一项就勾选一项并继续下一项，不因单项完成返回主线程等待再次派发。程序员子代理只有在全部程序员任务完成、阻塞、失败、需拆分、需复测或上下文不足时才返回并写入程序员结果。主线程读取程序员结果的 `## 主线程摘要` 后，再决定进入启动阶段、回到需求架构闸门、创建接力程序员或反馈用户。只要摘要显示仍有未完成程序员任务且不属于无法继续的阻塞，就必须先让同一个程序员子代理继续本阶段；所有这些任务未完成前，不得进入启动阶段或测试阶段。
5. 启动阶段：启动子代理通常只创建一个，用于连续准备测试环境、检查端口和健康状态、维护项目启动记录。只有需求架构摘要显示不需要程序员阶段，或程序员结果确认已完成本轮全部程序员任务后，才允许进入启动阶段。需要服务参与时，只能通过项目约定宿主入口拉起服务；如果需求架构或程序员子代理摘要说明服务、宿主入口、启动脚本、宿主桥接、静态资源托管、CORS 或数据库迁移发生变化，必须先让本轮启动子代理刷新启动状态再测试。主线程只能派发启动子代理并读取项目启动记录的 `## 主线程摘要`，不得自己执行启动诊断命令、读取长启动日志或更新启动状态。
6. 测试阶段：只有项目启动记录的 `## 主线程摘要` 显示可进入测试，且本轮没有未完成程序员任务时，主线程才按需求架构子代理摘要中的测试范围创建唯一测试子代理并串行执行测试项。全量测试场景下也不能并行测试；同一个测试子代理按测试项顺序依次执行浏览器端、宿主端或两者都需要的验证。只用浏览器测试场景的唯一测试子代理只执行验证端为浏览器端的测试项，不执行宿主端测试项；但仍不能跳过前置程序员阶段。测试阶段发现本轮测试计划缺失或结构不合格时，测试子代理必须停止并反馈需求架构闸门，主线程不得临时补写后继续测试。
7. 测试计划更新：测试子代理每完成一项测试，在主线程授权下更新本轮测试计划中对应状态、结果、失败原因、复现步骤、反馈对象和复测状态；未获授权时先写入自己的结果文件，由主线程串行合并。状态至少包括：`待测试`、`测试中`、`通过`、`失败待修复`、`已修复待复测`、`阻塞`。
8. 闭环回流：如果启动或测试返回阻塞，主线程先按结果文件 `## 主线程摘要` 判断归属。代码、脚本、端口配置、宿主入口拉起服务、依赖版本或打包装配问题回到原程序员子代理；启动命令选择、运行状态刷新或启动记录问题回到启动子代理；页面、浏览器端或宿主端复测问题回到测试子代理；用户电脑缺环境、权限、账号密钥或外部端口占用且代理无权处理时才反馈用户。程序员修复后在授权范围内把相关测试项状态改为 `已修复待复测`，未获授权时写入程序员结果等待主线程合并；可继续推进时不得直接进入最终汇总。
9. 完成标记：唯一测试子代理在完成全部指定测试范围后，必须重新读取完整本轮测试计划；只有所有必测项均为 `通过`，且没有阻塞、失败待修复或未复测项时，才负责把临时需求文件中对应一级标题追加 `-完成`，不再创建检验子代理。
10. 最终汇总：最终用中文汇总修改范围、需求同步、计划同步、架构同步、测试或构建结果、本轮测试计划最终状态、未测试项、未构建项和风险；如果仍阻塞，必须满足主线程职责中的阻塞终止条件。

## 子代理创建提示压缩规则

- 对子代理只写“请读取公共模板和某某子代理提示词”，不要粘贴公共模板全文、角色模板全文或任何业务文件正文。
- 创建或复用子代理前，主线程先更新本轮子代理登记文件；给子代理的消息只引用该登记文件路径，不复制已有子代理列表。
- 已经写入本轮计划的任务拆分，不要在子代理提示里重复展开；给程序员子代理时只给本轮计划路径、全部未完成程序员任务编号和文件范围，并明确要求连续执行，不要按单项任务逐个派发。
- 已经写入本轮测试计划的测试项，不要在子代理提示里重复展开，只给本轮测试计划路径、测试项编号和适用测试范围。
- 已经写入项目启动记录的启动信息，不要在测试子代理提示里重复展开，只给文件路径。
- 程序员、启动和测试子代理需要了解上下游结果时，只传对应结果文件路径和 `## 主线程摘要` 读取要求；不要在主线程消息中复述摘要正文。
- 子代理结果必须写入指定结果文件；返回主线程的消息只允许包含 `状态：...` 和 `结果文件：...`。
